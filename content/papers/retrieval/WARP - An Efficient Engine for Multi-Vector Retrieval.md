# A) 검색 방식의 흐름

WARP 는 multi-vector 검색을 실서비스에 쓸 수 있을 만큼 빠르게 만드는 검색 엔진이다. 정보 검색 방식은 대략 세 단계로 발전해 왔다.

* **키워드 검색 (예: BM25)**: 문서에 특정 단어가 몇 번 나오는지 세어 점수를 매긴다.
	* 단순하고 빠르다.
	* '자동차'와 '탈것'처럼 뜻은 같고 글자가 다른 단어는 잘 못 찾는다.
* **Single-vector 검색 (Single-Vector Retrieval)**: 문서 전체의 의미를 하나의 벡터로 압축한다.
	* '자동차'와 '탈것'이 비슷한 의미라는 것을 벡터 공간의 가까운 거리로 표현할 수 있어 의미 기반 검색이 된다.
	* 문서 내용을 벡터 하나에 압축하다 보니 세부 내용이나 뉘앙스를 놓친다.
* **Multi-vector 검색 (Multi-Vector Retrieval, 예: ColBERT, XTR)**: 문서에 포함된 토큰(단어 혹은 단어의 일부)마다 벡터를 하나씩 만든다.
	* 예를 들어 "워프는 빠른 검색 엔진이다"라는 문장이면 '워프', '빠른', '검색', '엔진'을 각각 벡터로 만들어 저장한다.
	* 의미를 더 정밀하게 표현할 수 있어 검색 정확도가 크게 오른다.

WARP 의 목표는 이 세 번째 방식인 multi-vector 검색을 실용 수준으로 빠르게 만드는 데 있다.

# B) 해결하려는 문제

## B.1) XTR (ConteXtualized Token Retriever)

XTR 은 "ConteXtualized Token Retriever"의 약자로, 직역하면 "문맥화된 토큰 검색기"다. ColBERT 의 아이디어를 한 단계 발전시켜 검색 과정을 단순화한 multi-vector 검색 모델이다.

기존 ColBERT 의 검색은 세 단계를 거친다.

1. **후보 찾기 (Token Retrieval)**: 검색어와 관련 있을 만한 문서 토큰을 먼저 찾는다.
2. **정보 모으기 (Gathering)**: 후보 토큰이 포함된 문서의 **모든** 토큰 벡터를 메모리로 불러온다. 이 단계가 매우 비효율적이고 느리다.
3. **점수 매기기 (Scoring)**: 불러온 정보를 종합해 최종 순위를 매긴다.

XTR 은 2번 Gathering 단계를 없앤다.

* **핵심 아이디어**: 문서의 모든 정보를 가져오지 않고, 1단계에서 뽑은 핵심 토큰 몇 개만으로 점수를 매긴다.
* **학습 방식**: 학습 단계부터 검색어와 가장 관련 있는 문서 토큰을 잘 찾아내도록 훈련한다.
	* 그래서 검색 시점에는 1단계에서 찾은 토큰의 정보만으로 바로 최종 점수를 계산할 수 있다.

## B.2) XTR 구현의 속도와 PLAID 의 최적화

XTR 은 이론적으로 효율을 높일 여지를 보여 줬지만, 공식 구현체는 최적화가 덜 되어 **실제 검색 속도가 매우 느리다.**

* LoTTE 데이터셋에서 검색 한 번에 6초 이상 걸렸다.

반면 [[ColBERT]] 를 빠르게 만든 **[[PLAID]]** 엔진은 압축, 가지치기(pruning) 같은 최적화로 속도를 크게 끌어올렸다.

저자들은 XTR 의 검색 방식과 PLAID 의 속도 최적화를 합치면 어떻게 될지를 묻고, 그 답으로 WARP 를 제안한다.

# C) 핵심 기법

WARP 는 XTR 의 검색 품질을 유지하면서 속도를 끌어올리기 위해 세 가지 기법을 쓴다.

## C.1) WARPSELECT: 누락 점수 추정

* **문제점**: XTR 은 검색어의 각 토큰(예: '빠른')마다 가장 관련 있는 문서 토큰 몇 개(예: '신속한', '고속의')와만 점수를 계산한다.
	* 나머지 문서 토큰과의 점수, 즉 누락된 점수(missing similarity)는 이미 찾은 점수 중 가장 낮은 값으로 채운다.
	* 이 방식은 부정확할 수 있다.
	* 점수를 더 정확하게 추정하려면 후보 토큰을 더 많이 찾아야 해서 속도가 느려진다.
* **WARP 의 해결책**: 문서 토큰을 미리 여러 클러스터로 묶어 두고, 검색어 토큰과 각 클러스터 대표 벡터(centroid)의 유사도를 활용한다.
	* WARPSELECT 는 이 클러스터 유사도로 모든 토큰을 비교하지 않고도 누락 점수를 빠르게 추정한다.
	* 후보를 찾는 과정에서 누락 점수까지 한 번에 계산한다.

### C.1.1) 클러스터링 방식

WARP 는 ColBERTv2/PLAID 의 방식을 그대로 따라 클러스터링한다.

1. **k-means 클러스터링**: 데이터베이스에 있는 모든 문서의 **모든 토큰 벡터**를 대상으로 k-means 를 적용한다.
2. **샘플링**: 수십억 개 토큰 벡터 전체를 클러스터링하면 비효율적이다.
	* 그래서 전체 문서 집합 크기의 제곱근(square root)에 비례하는 수의 문서 토큰을 무작위로 샘플링해 클러스터링한다.
	* 이렇게 만든 centroid 가 전체 데이터 분포를 잘 대표한다고 가정한다.
3. **인덱스 생성**: 각 문서 토큰 벡터를 가장 가까운 centroid 의 클러스터에 할당한다.
	* 인덱스에는 각 토큰 벡터가 어느 클러스터에 속하는지 같은 정보를 저장한다.

### C.1.2) IVF 인덱스와의 비교

WARPSELECT 의 클러스터링은 IVF 인덱스(Inverted File Index)와 개념적으로 매우 비슷하다.

* **IVF 인덱스**: 벡터를 몇 개의 centroid 기준으로 묶고(클러스터링), 각 벡터가 어느 클러스터에 속하는지 기록한다.
	* 검색할 때는 모든 벡터를 뒤지지 않고 검색어 벡터와 가장 가까운 몇 개 클러스터만 탐색해 속도를 높인다.
* **공통점**: k-means 로 탐색 공간을 줄이고, 검색어와 가까운 일부 클러스터(`nprobe`개)만 탐색한다.
* **차이점**: IVF 는 탐색 대상을 줄이는 데서 끝나지만, WARPSELECT 는 이 클러스터 구조로 누락 점수까지 추정한다.
	* 검색 시 검색어 토큰과 가장 가까운 `nprobe`개 centroid 와의 유사도를 계산한다.
	* 이 유사도를 정렬한 뒤, 누적 클러스터 크기가 임계값 t' 을 넘는 지점의 점수를 누락 점수로 쓴다.
	* 즉 클러스터링을 **(1) 탐색 공간 축소**와 **(2) 점수 추정**에 함께 쓴다.

### C.1.3) 쿼리 토큰별 누락 점수

**한 검색어(query) 안에서 특정 쿼리 토큰의 누락 점수는 모든 문서에 똑같이 적용된다.** 다만 쿼리 안의 서로 다른 토큰은 서로 다른 누락 점수를 가진다.

"가장 빠른 CPU" 쿼리로 예를 들면 다음과 같다.

1. **쿼리 분해**: 쿼리를 3개 토큰으로 나눈다.
	* `q1` = "가장"
	* `q2` = "빠른"
	* `q3` = "CPU"
2. **토큰별 누락 점수 계산 (WARPSELECT)**:
	* **`q1` ("가장")**: "가장" 벡터와 모든 centroid 벡터의 유사도를 계산하고, 임계값 t' 규칙을 적용해 누락 점수 `m1` 을 정한다 (예: `m1` = 0.15).
	* **`q2` ("빠른")**: 같은 과정으로 `m2` 를 정한다 (예: `m2` = 0.35).
	* **`q3` ("CPU")**: 같은 과정으로 `m3` 를 정한다 (예: `m3` = 0.40).

이 검색에서는 `m1=0.15`, `m2=0.35`, `m3=0.40` 세 값이 **고정된 누락 점수**가 된다. 문서별 점수를 계산할 때 이 값을 다음처럼 쓴다.

* **문서 A (관련 토큰이 일부 없음)**:
	* "가장"에 대한 최고점: 0.7
	* "빠른"에 대한 최고점: **없음 → 누락 점수 `m2` (0.35) 적용**
	* "CPU"에 대한 최고점: 0.95
	* **최종 점수 = 0.7 + 0.35 + 0.95 = 2.0**
* **문서 B (다른 토큰이 없음)**:
	* "가장"에 대한 최고점: **없음 → 누락 점수 `m1` (0.15) 적용**
	* "빠른"에 대한 최고점: 0.9
	* "CPU"에 대한 최고점: **없음 → 누락 점수 `m3` (0.40) 적용**
	* **최종 점수 = 0.15 + 0.9 + 0.40 = 1.45**
* **문서 C (관련 토큰이 모두 있음)**:
	* "가장"에 대한 최고점: 0.6
	* "빠른"에 대한 최고점: 0.88
	* "CPU"에 대한 최고점: 0.92
	* **최종 점수 = 0.6 + 0.88 + 0.92 = 2.4**

이 방식의 장점은 두 가지다.

* **공정성**: 특정 쿼리 토큰(예: "빠른")과 관련된 정보가 없는 문서는 모두 **같은 페널티**(누락 점수 `m2`)를 받는다.
	* 모든 문서를 같은 기준선에서 평가하게 된다.
* **효율성**: 누락 점수는 쿼리 토큰마다 한 번만 계산하면 된다.
	* 문서마다 누락 점수를 따로 계산해야 했다면 검색이 훨씬 복잡하고 느려진다.

## C.2) Implicit Decompression: 압축 해제 없는 점수 계산

* **문제점**: multi-vector 검색은 토큰 벡터를 매우 많이 저장해야 해서 용량이 크다.
	* 그래서 PLAID 같은 엔진은 벡터를 압축해 저장하고, 검색 시점에 압축을 푼다(decompression).
	* 이 압축 해제 과정이 상당한 시간을 잡아먹는 병목이었다.
* **WARP 의 해결책**: 필요한 것은 최종 유사도 점수뿐이므로, 압축된 벡터를 원래 형태로 복원하지 않고 **압축된 상태에서 바로 점수를 계산**한다.
	* 이 기법(Implicit Decompression) 덕분에 속도 저하의 주범이던 압축 해제 단계를 사실상 건너뛴다.

### C.2.1) 잔차 양자화 (Residual Quantization)

압축된 상태에서 계산이 가능한 이유는 잔차 양자화(Residual Quantization) 덕분이다. 벡터를 통째로 압축하지 않고, 기준점에서 얼마나 떨어져 있는지를 나타내는 **잔차**(residual)만 작게 압축해 저장한다.

1. **기준점 설정**: 클러스터링으로 각 토큰은 특정 클러스터에 속한다. 소속 클러스터의 **centroid 벡터가 기준점**이 된다.
2. **잔차 계산**: `[실제 토큰 벡터] - [소속된 클러스터의 중심점 벡터] = [잔차(Residual) 벡터]`
	* 실제 토큰 벡터는 128차원 float32 벡터다.
	* 잔차 벡터는 그보다 훨씬 작은 값으로 이루어진다.
3. **잔차 양자화 (Quantization)**: 잔차 벡터를 압축한다.
	* 양자화는 연속적인 값을 몇 개의 대표값으로 근사하는 과정이다 (예: 1.13, 1.18, 1.24 를 대표값 1.2 하나로 통일).
	* WARP 는 잔차 벡터의 각 차원(128개)을 **4비트 정수**(0–15)로 압축한다.
	* 32비트 실수 하나가 4비트 정수 하나로 바뀌므로 **데이터 크기가 1/8 로 줄어든다** (8x 압축).

### C.2.2) 압축 상태에서의 점수 계산

구하려는 점수는 `(검색어 토큰 벡터) · (문서 토큰 벡터)` 다 (·은 내적, 즉 유사도 계산).

1. **수식 분해**: `문서 토큰 벡터`는 `중심점 벡터 + 잔차 벡터` 이므로 다음처럼 쓸 수 있다.
	* `유사도 점수 = (검색어 벡터) · (중심점 벡터 + 잔차 벡터)`
2. **분배 법칙 적용**: 내적의 분배 법칙으로 전개한다.
	* `유사도 점수 = (검색어 벡터 · 중심점 벡터) + (검색어 벡터 · 잔차 벡터)`
3. **두 항의 계산**:
	* **(검색어 벡터 · 중심점 벡터)**: WARPSELECT 단계에서 후보 클러스터를 찾을 때 이미 계산해 둔 값이라 그대로 재사용한다.
	* **(검색어 벡터 · 잔차 벡터)**: 이 항만 새로 계산한다. 압축된 4비트 잔차를 그대로 쓰는 최적화된 C++ 커널로 계산하므로, 압축을 완전히 푸는 것보다 훨씬 적은 연산으로 근사 계산이 된다.

결국 128차원 벡터를 복원한 뒤 내적하는 대신, 계산을 둘로 나눠 처리한다.

1. **이미 계산된 값을 재사용한다 (`Query · Centroid`).**
2. **압축된 작은 값에 대한 가벼운 연산을 더한다 (`Query · Residual`).**

이렇게 해서 압축 해제라는 병목을 건너뛰고 최종 점수를 훨씬 빠르게 얻는다. 이것이 Implicit Decompression 의 원리다.

## C.3) Two-Stage Reduction: 최종 점수 합산

* **문제점**: 검색어의 모든 토큰과 후보 문서의 모든 토큰 사이 점수를 계산하면 거대한 점수표(score matrix)가 생긴다.
	* 이 표를 만들고 행(문서)별로 점수를 합산하는 과정은 메모리를 많이 쓰고 계산도 비효율적이다.
* **WARP 의 해결책**: 이 과정을 두 단계로 나눈다.
	1. **토큰 레벨 축소**: 쿼리 토큰과 문서 쌍마다 가장 높은 점수(최댓값)만 남긴다.
	2. **문서 레벨 축소**: 줄인 점수를 문서별로 합산해 최종 문서 점수를 구한다. 이때 WARPSELECT 로 추정한 누락 점수도 함께 더한다.
* **효과**: 거대한 중간 결과물을 만들지 않으므로 메모리 사용량이 줄고 계산 속도가 크게 오른다.

# D) 검색 과정 단계별 정리

"가장 빠른 CPU" 쿼리를 예로 든다.

**Phase 1: 쿼리 분석 및 준비 (검색 시작 시 한 번 수행)**

1. **쿼리 토큰 분해**: "가장 빠른 CPU" → `q1`("가장"), `q2`("빠른"), `q3`("CPU")
2. **WARPSELECT 실행**:
	* **누락 점수 계산**: 각 쿼리 토큰(`q1`, `q2`, `q3`)과 모든 centroid 의 유사도를 계산해 누락 점수 `m1`, `m2`, `m3` 를 **미리 확정**한다.
	* **탐색할 클러스터 선정**: 각 쿼리 토큰마다 탐색할 상위 `nprobe`개 클러스터를 정한다.

**Phase 2: 점수 계산 및 집계**

선정된 클러스터를 순회하며 실제 점수를 계산한다. `q2`("빠른") 토큰에 대한 문서 D 의 점수를 예로 든다.

1. **관련 클러스터 탐색**: "빠른" 토큰과 가깝다고 선정된 `nprobe`개 클러스터를 본다.
2. **클러스터 내 문서 토큰 처리**: 그 클러스터 안의 **모든 문서 토큰**을 하나씩 본다.
3. **점수 계산 (잔차 활용)**:
	* 클러스터 안에서 문서 D 에 속한 토큰(예: "고속")을 발견한다.
	* "고속" 토큰의 점수는 잔차를 활용해 계산한다.
	* **`실제 점수 = (q2 • 대표점 벡터) + (q2 • "고속"의 잔차 벡터)`**
	* `(q2 • 대표점 벡터)`는 이미 계산되어 있고, `(q2 • "고속"의 잔차 벡터)`는 미리 만들어 둔 룩업 테이블로 빠르게 계산한다.
4. **문서 D 내 최고점(MaxSim) 찾기**:
	* `nprobe`개 클러스터를 모두 탐색하면 문서 D 에 속한 토큰("고속", "신속한" 등)이 여러 개 나올 수 있다.
	* 이 점수를 모두 비교해 `q2`("빠른")에 대해 문서 D 가 얻는 **가장 높은 점수 하나만** 남긴다 (예: 0.9점).

**Phase 3: 최종 점수 합산 (Document-Level Reduction)**

모든 쿼리 토큰(`q1`, `q2`, `q3`)에 대해 Phase 2 가 끝나면 문서별 최종 점수를 합산한다.

* **문서 D 의 최종 점수**:
	* `q1`에 대한 최고점: 0.7 (찾음)
	* `q2`에 대한 최고점: 0.9 (찾음)
	* `q3`에 대한 최고점: **없음 → 누락 점수 `m3`(0.40) 적용**
	* **합산**: 0.7 + 0.9 + 0.40 = 2.0

**점수의 출처**는 두 가지다.

* **찾은 경우**: 클러스터 안의 문서 토큰과 쿼리 토큰 사이 거리를 쓴다.
	* 이 계산에는 클러스터 대표점과 잔차를 활용한다.
* **못 찾은 경우**: 클러스터 레벨에서 미리 계산해 둔 누락 점수를 쓴다.

이 구조로 WARP 는 정확도를 유지하면서 불필요한 계산을 크게 줄인다.

# E) 실험 결과

* **속도 (Latency)**:
	* 최적화되지 않은 기존 XTR 구현보다 LoTTE 데이터셋에서 **41배 빠르다** (6,862ms → 171ms).
	* 잘 최적화된 ColBERTv2/PLAID 엔진보다도 **3배 빠르다** (476ms → 171ms).
	* CPU 코어 여러 개를 쓰는 병렬 처리도 잘 된다. 16개 스레드를 쓰면 3.1배 더 빨라진다.
* **정확도 (Retrieval Quality)**:
	* 속도를 크게 올리면서도 **검색 정확도는 거의 떨어지지 않았다.**
	* 일부 데이터셋에서는 오히려 조금 올랐다.
* **메모리 사용량 (Memory Footprint)**:
	* 벡터 압축을 쓰므로 압축하지 않은 원본(BruteForce)이나 ScaNN 기반 XTR 보다 인덱스 파일이 훨씬 작다.
	* 예를 들어 전체 테스트 데이터셋에서 ScaNN 방식 대비 **메모리 사용량을 절반(2x)으로 줄였다.**
	* 자원이 제한된 실서비스 환경에서 큰 장점이다.

# F) 의의

1. **실서비스 수준의 구현**: 정확도는 높지만 너무 느려 쓰기 어려웠던 XTR 을 **실서비스에 적용할 수 있을 만큼 빠르고 효율적인 시스템**으로 구현했다.
2. **두 연구 갈래의 결합**: XTR 의 검색 구조와 PLAID 의 최적화 기법을 합쳐, 기존 최고 성능 엔진보다 빠른 결과를 냈다.
3. **실용성**: 메모리를 적게 쓰고 CPU 자원을 효율적으로 활용하도록 설계해, 다양한 환경에 배포하기 적합하다.
