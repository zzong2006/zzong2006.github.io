# 핵심 요약

- **Hash-based embedding 은 ID 하나에 해시 함수를 여러 개 적용해 임베딩 테이블의 칸을 여러 개 고르고, 그 칸들의 벡터를 합쳐 쓴다.**
  - 사전 없이 새 ID 도 바로 칸을 받는 [[hashing trick]] 의 장점은 그대로다.
- **해시가 하나면 같은 칸에 든 두 ID 가 완전히 같은 벡터를 쓰지만, 해시가 둘이면 두 칸이 모두 겹치는 일이 거의 없다.**
  - ID 1억 개를 칸 1억 개에 넣을 때 완전히 겹치는 쌍이 거의 사라진다 (해시 1 개 약 5천만 쌍 → 해시 2 개 약 0.5 쌍).
- **X 의 추천 모델 Phoenix 가 이 방식을 쓴다.**
  - 사용자·게시물·작성자·IP 마다 해시를 2 개씩 쓰고, 칸마다 다른 변환을 곱한 뒤 더한다.
- **해시는 새 게시물에 칸을 줄 뿐, 의미 있는 벡터까지 주지는 않는다.**
  - Phoenix 는 게시물 내용을 담은 semantic ID 로 이 빈틈을 메운다.

# A) 해시 하나일 때의 한계

[[hashing trick]] 노트와 같은 쇼핑몰 클릭 예측 모델을 생각하자. 상품 ID 를 사전 대신 해시 함수로 임베딩 테이블의 칸에 넣는다. 칸은 테이블의 행 하나이고, 칸마다 숫자 묶음(벡터)이 하나씩 있다.

**사전 대신 해시를 쓰는 이유는 새 ID 가 바로 칸을 받기 때문이다.**

- X 같은 피드에서는 게시물이 초 단위로 생긴다.
- 사전을 하루에 한 번 다시 만든다면, 오늘 올라온 글은 하루 동안 사전에 없는 "모르는 게시물" 하나로 묶인다.
- 새 글을 빨리 보여 주는 것이 목적인 피드에서는 받아들일 수 없는 일이다.

**해시가 하나면 같은 칸에 든 두 상품은 완전히 같은 벡터를 쓴다.**

- 모델은 두 상품을 구분할 방법이 없다.
- 이런 충돌은 드물지 않다. 상품 1억 개를 칸 1억 개에 넣으면 같은 칸을 쓰는 상품 쌍이 약 5천만 쌍이다.
- 칸을 늘리면 충돌이 줄지만, 테이블도 그만큼 커진다.

# B) 해시 여러 개로 칸 여러 개 고르기

해시 함수를 서로 다른 것으로 두 개 둔다. 상품마다 첫 번째 해시로 칸 하나, 두 번째 해시로 칸 하나를 고르고, 두 칸의 벡터를 더한 것을 그 상품의 벡터로 쓴다. 아래 그림의 칸 번호는 설명을 위해 정한 값이다.

![[img-3db38c160d.png]]

**운동화와 가방은 1번 칸을 나눠 쓰지만, 최종 벡터는 다르다.**

- 두 번째 해시에서 운동화는 5번, 가방은 3번 칸을 받았다.
- 두 상품이 완전히 같은 벡터를 쓰려면, 두 해시 모두에서 같은 칸을 받아야 한다.

**칸 하나만 나눠 쓰는 일(부분 충돌)은 그대로 남는다.**

- 운동화와 우산은 5번 칸을 나눠 쓴다. 5번 칸의 벡터는 두 상품의 기록을 함께 배운다.
- 나머지 칸이 다르므로 두 상품이 하나로 합쳐지지는 않는다. 벡터에 상대 상품의 기록이 조금 섞이는 정도로 끝난다.

**두 칸이 모두 겹칠 확률은 해시를 하나 더할 때마다 크게 준다.** 상품 1억 개를 칸 1억 개에 넣는 경우다.

- 해시 1 개: 같은 칸을 쓰는 상품 쌍이 약 5천만 쌍
- 해시 2 개: 두 칸이 모두 같은 쌍이 약 0.5 쌍
- 해시 3 개: 사실상 0

상품 두 개가 칸 하나에서 겹칠 확률은 1억 분의 1 이다. 두 칸 모두 겹치려면 이 확률을 두 번 곱해야 하므로 1경 분의 1 로 떨어진다. 식은 부록 「완전 충돌 확률」 에 있다.

독립 해시 여러 개를 겹쳐 충돌의 영향을 흩는 생각은 [[Count Sketch]] 나 Bloom filter 와 같은 계열이다.

# C) Phoenix: 칸마다 다른 변환을 곱한 뒤 더하기

X 가 공개한 For You 피드 알고리즘(`xai-org/x-algorithm`)의 Phoenix 모델은 후보를 고르는 retrieval 과 순위를 매기는 ranking 양쪽에서 이 구조를 쓴다. 다만 두 칸의 벡터를 그냥 더하지 않는다.

**첫 번째 해시로 고른 칸과 두 번째 해시로 고른 칸에, 각각 다른 projection 행렬을 곱한 뒤 더한다.**

- projection 행렬은 벡터의 길이와 방향을 바꾸는 선형 변환이다.
- 이유 1: 테이블 칸의 벡터 길이(1024)와 모델이 쓰는 벡터 길이(2560)가 달라서, 어차피 변환이 한 번 필요하다.
- 이유 2: 같은 칸이 어떤 상품에서는 첫 번째 해시로, 다른 상품에서는 두 번째 해시로 뽑힐 수 있다. 해시마다 변환이 다르면 모델이 두 역할을 구분해 쓸 수 있다.

**게시물 하나를 나타낼 때는 칸 네 개를 읽는다.**

- 게시물 ID 해시 2 개와 작성자 ID 해시 2 개다.
- 네 칸을 각자의 변환에 통과시킨 뒤 더한 것이 그 게시물의 벡터다.

나머지 구현은 다음과 같고, 식과 숫자는 부록 「Phoenix 구현 세부」 에 있다.

- 사용자·게시물·작성자·IP 네 종류가 모두 해시를 2 개씩 쓴다.
- 해시 함수는 곱하고 더하고 나머지를 구하는 단순한 식이다. 상수가 설정 파일에 고정돼 있어 학습과 서빙이 같은 칸을 본다.
- 0번 칸은 값이 없을 때 쓰는 자리(padding)로 비워 둔다.
- 네 종류가 큰 테이블 하나를 구간으로 나눠 쓴다. 사용자 1억, 게시물 1억, 작성자 3천만, IP 1천만 칸이다.
- 테이블이 fp32 기준 약 983 GB 라 GPU 한 장에 들어가지 않는다. 그래서 테이블을 저장하고 읽는 전용 경로를 따로 둔다.

# D) 해시가 해 주지 못하는 것

**새 게시물은 칸을 바로 받지만, 그 칸의 벡터는 아직 이 게시물에 대해 배운 것이 없다.**

- 칸을 받는 것과 벡터가 학습된 것은 다르다.

**내용이 비슷한 두 게시물도 ID 가 다르면 전혀 상관없는 칸으로 간다.**

- 해시는 의미를 보존하지 않는다. ID 해시만으로는 "비슷한 글이니 비슷하게 다룬다" 를 배울 수 없다.

Phoenix 는 이 빈틈을 semantic ID 로 메운다.

# E) semantic ID: 내용으로 만든 ID

**semantic ID 는 게시물 내용을 담은 벡터를 짧은 코드 몇 개로 바꾼 것이다.**

- 입력은 게시물의 텍스트와 이미지를 함께 인코딩한 벡터다([[CLIP]] 계열).
- Phoenix 는 이 벡터를 코드 6 개로 바꾼다. 각 코드는 1 부터 256 사이의 번호다. 0 은 값이 없을 때 쓴다.
- 해시와 달리, 내용이 비슷한 게시물은 비슷한 코드를 받는다.

## E.1) 코드 생성 방식: residual quantization

**한 단계에서 벡터와 가장 가까운 대표 벡터를 고르고, 다음 단계에서 남은 차이를 다시 근사한다.**

- 단계마다 대표 벡터 목록이 하나씩 있다. 이 목록을 코드북(codebook)이라 하고, 목록 안의 번호가 코드다.
- 1단계 코드북은 게시물 벡터 전체를 큰 묶음으로 나눈 대표점이다. 뒤 단계 코드북은 남은 작은 차이를 나눈 대표점이다.

2차원 벡터에 단계마다 코드 4 개인 작은 예시로 보자. 1단계 코드북은 (−5, 5), (5, 5), (−5, −5), (5, −5) 이고, 2단계 코드북은 (0, 1), (1, 0), (0, −1), (−1, 0) 이다. 게시물은 축구 (5.9, 5.2), 농구 (4.8, 6.1), 파스타 (−4.1, −5.3) 세 개다. 숫자는 설명을 위해 정한 값이다.

![[img-aecf9e7d14.png]]

축구 게시물을 따라가 보면 다음과 같다.

1. 1단계: 가장 가까운 코드는 2번 (5, 5) 다. 남은 차이(잔차)는 (5.9, 5.2) − (5, 5) = (0.9, 0.2) 다.
2. 2단계: 잔차 (0.9, 0.2) 와 가장 가까운 코드는 2번 (1, 0) 이다. 이제 남은 차이는 (−0.1, 0.2) 로 작다.
3. 축구의 semantic ID 는 (2, 2) 다. 두 코드의 벡터를 더한 (6, 5) 가 원래 벡터 (5.9, 5.2) 에 가깝다.

세 게시물의 결과는 축구 (2, 2), 농구 (2, 1), 파스타 (3, 2) 다.

- **벡터가 가까운 게시물은 앞쪽 코드를 공유한다.**
  - 축구와 농구는 1단계 코드가 2 로 같다.
- **뒤쪽 코드는 앞쪽 코드 안에서의 세부 위치만 뜻한다.**
  - 파스타는 2단계 코드가 축구와 같은 2 지만, 1단계가 달라 전혀 다른 곳에 있다.

식으로 쓰면 다음과 같다.

$$
\mathbf{r}_0 = \mathbf{x}, \qquad c_l = \arg\min_{k} \lVert \mathbf{r}_{l-1} - \mathbf{C}_l[k] \rVert, \qquad \mathbf{r}_l = \mathbf{r}_{l-1} - \mathbf{C}_l[c_l]
$$

- $\mathbf{x}$ 는 게시물 벡터, $\mathbf{C}_l[k]$ 는 $l$ 단계 코드북의 $k$ 번 코드 벡터다.
- $c_l$ 은 $l$ 단계에서 고른 코드이고, $\mathbf{r}_l$ 은 $l$ 단계 뒤에 남은 차이다.
- 6 단계를 마치면 semantic ID 는 $(c_1, \ldots, c_6)$ 이고, 원래 벡터는 코드 벡터의 합 $\mathbf{C}_1[c_1] + \cdots + \mathbf{C}_6[c_6]$ 으로 근사된다.
- 코드북을 만드는 학습 코드도 공개돼 있다(`phoenix/reference/sid_codebook.py`). 단계마다 k-means 로 대표점을 정하는 RQ-KMeans 와, 신경망과 함께 학습하는 RQ-VAE 를 지원한다. 운영에서 어느 쪽을 쓰는지는 확인 필요.

## E.2) 모델 입력 방식

**코드 번호마다 학습되는 벡터를 하나씩 두고, 6 단계에서 꺼낸 벡터를 합친다.**

- 단계마다 행 257 개(코드 256 개와 값 없음 0번)짜리 임베딩 표가 따로 있다.
- 축구 (2, 2) 라면 1단계 표의 2번 벡터와 2단계 표의 2번 벡터를 꺼내 더한다.

$$
\mathbf{e}_{\text{sid}} = \mathbf{T}_1[c_1] + \mathbf{T}_2[c_2] + \cdots + \mathbf{T}_6[c_6]
$$

- $\mathbf{T}_l$ 은 $l$ 단계의 임베딩 표다. 코드를 정할 때 쓴 코드북 $\mathbf{C}_l$ 과 달리, 클릭 예측을 학습하면서 같이 고쳐진다.
- 실제로는 기본 설정(`sid_cross_attn=True`)에서 단계별 벡터끼리 attention 을 한 번 거친 결과와 원래 벡터를 각각 평균내 더한다. 그다음 모델 폭에 맞게 projection 을 곱한다.

**그래서 처음 보는 게시물도 의미 있는 벡터를 받는다.**

- 새 축구 게시물이 (2, 3) 을 받았다면, 1단계 표의 2번 벡터는 이미 축구·농구 같은 글로 학습돼 있다.
- ID 해시로 받은 칸이 아직 아무것도 배우지 않은 벡터라는 점과 다르다.
- 그래서 [[cold-start]] 상황에서 도움이 된다.

## E.3) ID 해시와 semantic ID 비교

| 구분 | ID 해시 | semantic ID |
| --- | --- | --- |
| 나타내는 것 | 이 게시물이 무엇인지 | 이 게시물의 내용이 무엇인지 |
| 처음 보는 게시물 | 칸은 생기지만 벡터는 아직 학습 전 | 학습된 코드의 조합으로 바로 의미를 표현 |
| 비슷한 게시물 | 서로 상관없는 칸으로 흩어짐 | 코드 앞부분을 공유 |
| 게시물 구분 | 칸 조합이 다르면 구분됨 | 내용이 같으면 구분 못 함 |

그래서 [[Two-tower Model|two-tower]] retrieval 의 후보 쪽은 게시물을 게시물 ID 해시가 아니라 semantic ID 와 작성자 해시로 나타낸다. 후보가 1천만 개 넘게 계속 바뀌는 상황에서 게시물 구분보다 내용 일반화를 택한 것이다.

# F) 도입할 때 정할 것

**칸 수는 학습 전에 정해야 하고, 곧 테이블 크기가 된다.**

- 칸 수가 테이블 행 수라서 GPU 메모리와 체크포인트 크기를 바로 결정한다.
- Phoenix 가 사용자·게시물에 1억, 작성자에 3천만, IP 에 1천만을 준 것도 종류별 고유값 수를 어림해 정한 값이다.

**해시 개수는 충돌과 비용을 맞바꾼다.**

- 해시를 늘리면 완전 충돌은 급격히 준다.
- 대신 읽는 칸 수와 변환 행렬 수가 해시 수만큼 늘어난다.
- Phoenix 는 모든 종류에 2 개를 쓴다. 칸을 고유값 수만큼 넉넉히 잡을 수 있으면 2 개로 충분하다는 판단으로 읽힌다.

**어떤 칸이 어떤 ID 의 것인지 거꾸로 알 수 없다.**

- 특정 게시물의 벡터만 골라 초기화하거나 지울 수 없다.
- 반대로 사전을 배포하다 실패하거나, 학습과 서빙의 사전이 어긋나는 사고는 아예 생기지 않는다.

**ID 종류가 많고, 계속 늘고, 새 ID 가 곧바로 서빙에 들어가야 할 때 쓸 만하다.**

- 피드, 광고([[CTR prediction]]), 커머스 검색처럼 아이템이 하루에도 여러 번 바뀌는 곳이 여기 해당한다.
- 아이템이 고정돼 있고 수십만 개 수준이면 사전을 두는 편이 충돌을 감수하는 것보다 싸다.

# G) 부록

## G.1) 완전 충돌 확률

서로 독립인 해시 함수 $k$ 개로 ID 마다 칸 $k$ 개를 뽑아, 해시마다 따로 둔 변환을 곱한 뒤 더한다.

$$
e(x) = \sum_{j=1}^{k} W_j \, E\big[h_j(x)\big]
$$

| 기호 | 뜻 |
| --- | --- |
| $x$ | 엔티티 ID (user ID, post ID 등) |
| $h_j$ | $j$ 번째 해시 함수. 출력은 칸 번호 |
| $E$ | 임베딩 테이블. 각 칸의 벡터 길이는 $d_{\text{table}}$ |
| $W_j \in \mathbb{R}^{d_{\text{table}} \times d_{\text{model}}}$ | $j$ 번째 해시 전용 projection 행렬 |
| $e(x)$ | 모델이 실제로 쓰는 $d_{\text{model}}$ 차원 표현 |
| $B$ | 칸 수 |
| $N$ | 실제 엔티티 개수 |

두 ID 가 완전히 같은 표현을 가지려면 $k$ 개 해시가 전부 같은 칸을 내야 하므로, 한 쌍이 완전히 겹칠 확률은 $B^{-k}$ 다. 쌍의 수는 약 $N^2/2$ 이므로 완전 충돌 쌍의 기대 개수는 $N^2 / (2B^k)$ 다.

| 해시 개수 $k$ | 한 쌍이 완전히 겹칠 확률 | $N = B = 10^8$ 일 때 완전 충돌 쌍의 기대 개수 |
| --- | --- | --- |
| 1 | $10^{-8}$ | 약 5천만 쌍 |
| 2 | $10^{-16}$ | 약 0.5쌍 |
| 3 | $10^{-24}$ | 사실상 0 |

## G.2) Phoenix 구현 세부

**해시 함수.** `xrex/models/recsys_embedding.py` 의 `HashTable` 클래스가 universal hashing 계열의 단순한 식을 쓴다.

$$
h_j(x) = \Big( \big( a_j x + b_j \big) \bmod p_j \Big) \bmod (B - 1) + 1
$$

- $a_j$(scale), $b_j$(bias), $p_j$(modulus)는 엔티티 종류마다 config 에 고정된 상수다. 예를 들어 item 쪽은 $a = [2161410491,\ 1754358832]$, $p = 2361375383$ 이다.
- 마지막의 `% (B-1) + 1` 은 결과를 $1$ 부터 $B-1$ 까지로 옮겨 0번 칸을 padding 자리로 비운다.
- ID 가 0(값 없음)이면 해시를 거치지 않고 그대로 0 을 내보내고, 모델은 `post_hashes[..., 0] != 0` 으로 padding mask 를 만든다.

**테이블 구간.** 해시 결과에 엔티티별 offset 을 더해 테이블 하나를 나눠 쓴다.

| 구간 | 시작 위치 | 크기 (production ranking 설정) |
| --- | --- | --- |
| padding | 0 | 1 |
| action 토큰 | 1 | 64 |
| user | 65 | 100M |
| item(post) | 65 + 100M | 100M |
| author | 65 + 200M | 30M |
| IP | 65 + 230M | 10M |

- 0번은 padding 이고, 1번부터 64번은 사용자 행동 종류(favorite, reply 같은 60 개를 64 로 올림한 것)를 나타내는 토큰 자리다.
- 행동 임베딩과 ID 임베딩이 같은 테이블에 있어, 시퀀스의 각 위치가 무엇인지를 같은 조회 한 번으로 처리한다.

**칸마다 변환을 곱하는 코드.** 슬롯마다 `user_hash_0_proj`, `user_hash_1_proj` 처럼 이름이 따로 붙은 projection 을 통과시킨 뒤 더한다.

```python
result = jnp.zeros((B, 1, D), dtype=fprop_dtype)
for i in range(num_user_hashes):
    h = user_embs[:, i : i + 1, :]
    result = result + _project_hash(h, f"user_hash_{i}_proj", config)
```

**규모와 엔지니어링.**

- 테이블 행 수는 약 2억 4천만, 행 폭은 1024 다. fp32 기준 $2.4 \times 10^8 \times 1024 \times 4\ \text{B} \approx 983\ \text{GB}$ 다.
- 학습 쪽은 `xrex/cuda/async_emb/` 의 CUDA 커널로 조회와 gradient 업데이트를 비동기로 겹치고, 옵티마이저도 행 단위로 상태를 갖는 `rowwise_adagrad` 를 쓴다.
- 서빙 쪽은 Rust 로 짠 `emb_table.rs` 가 huge page 를 잡아 gather 를 처리한다.
- ranking 모델은 한 예시마다 history 1022 개와 candidate 64 개를 시퀀스로 받고 각 위치가 4 번 조회하므로, 예시 하나에 4천 행 이상을 읽는다. 그래서 조회 전에 `compress_token_ids` 로 배치 안의 중복 ID 를 먼저 unique 처리한다.

**`sid_hash_level` 옵션.** 켜면 semantic ID 6 단계 뒤에 post ID 해시를 코드북 크기(256)로 한 번 더 접은 값을 7 번째 단계처럼 붙인다. 내용으로 설명되는 부분은 앞 6 단계가 맡고, 내용만으로는 구분되지 않는 게시물 고유의 차이를 마지막 한 칸이 받는다.
